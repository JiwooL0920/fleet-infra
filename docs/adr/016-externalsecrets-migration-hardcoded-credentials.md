# ADR-016: Migrate Hardcoded Credentials to ExternalSecrets

**Status:** Accepted
**Date:** 2026-07-03

## Context

The March 2026 audit ([docs/audit_031226_1773354880.md](../audit_031226_1773354880.md))
identified three services with committed credentials in Git:

- `apps/base/n8n/helmrelease.yaml:46` — `encryption_key: "n8n-encryption-key-change-me"`
- `apps/base/weave-gitops/helmrelease.yaml:44` — bcrypt `passwordHash` hardcoded
- `apps/base/pgadmin4/helmrelease.yaml:41` — hardcoded admin email

The July 2026 audit re-verified these findings and confirmed all three remained unfixed
across the intervening 4 months. ADR-005 established LocalStack + ExternalSecrets as the
canonical development-time secret pattern, and 7 services already follow it consistently.

## Decision

Migrate the three remaining hardcoded credentials into the ExternalSecrets pattern
established by ADR-005. Each secret follows the same flow:

1. Value generated by LocalStack init script (`apps/base/localstack/helmrelease.yaml`)
2. Stored in LocalStack Secrets Manager under a canonical path
3. Synced into Kubernetes by an `ExternalSecret` resource in the service's namespace
4. Consumed by the HelmRelease via `existingSecret` / `valueFrom.secretKeyRef`

### Per-Service Approach

| Service | LocalStack Path | K8s Secret Name | Chart Consumption |
|---|---|---|---|
| n8n | `n8n/credentials/encryption-key` | `n8n-encryption-key` (ns: n8n) | `main.extraEnv.N8N_ENCRYPTION_KEY.valueFrom.secretKeyRef` |
| weave-gitops | `weave-gitops/admin/credentials` (JSON) | `cluster-user-auth` (ns: weave-gitops) | Chart-required Secret name; set `adminUser.create: false` |
| pgadmin4 | `pgadmin4/credentials/password` | `pgadmin4-credentials` (ns: pgadmin4) | **Already migrated** — verified via `pgadmin4-credentials` ExternalSecret |

### Special Cases

- **pgadmin4 email:** The `pgadmin4` chart's `env.email` field does not support loading
  from a Secret. Email remains inline in `apps/base/pgadmin4/helmrelease.yaml` as an
  accepted chart limitation. Email is not sensitive (no auth value on its own).
- **weave-gitops Secret name:** The `weave-gitops` chart specifically looks for a Secret
  named `cluster-user-auth` in the target namespace. The ExternalSecret target uses this
  exact name; cutover requires setting `adminUser.create: false` in the same commit as the
  ExternalSecret kustomization insertion (Wave 2B — T11) to avoid conflict with chart-owned
  Secret ownership.
- **bcrypt cost:** LocalStack init generates weave-gitops passwordHash with bcrypt cost 10
  per chart docs. `htpasswd -bnBC 10 "" "$RANDOM_PWD" | tr -d ':\n' | sed 's/$2y/$2a/'`
  produces a valid `$2a$` hash.

### Rollout Sequence

**Wave 2A (additive setup)** — this commit and prior:

- Add ExternalSecret manifests (n8n, weave-gitops)
- Add LocalStack init entries to seed new secret values
- pgadmin4 already ES-managed — verified

**Wave 2B (atomic cutover)** — per-service, one commit each:

1. `flux suspend kustomization <svc>`
2. Verify ES-generated Secret has expected keys
3. Delete committed credential from HelmRelease; reference ES Secret via chart values
4. Commit
5. `flux resume kustomization <svc>` + rollout restart
6. Verify service functional via HTTP check

Per-service commits provide atomic revert if cutover breaks the service.

## Consequences

### Positive

- Zero plaintext credentials in Git after Wave 2B completes
- Consistent pattern across 10+ services (7 pre-existing + 3 new)
- Secret rotation is a single operation on LocalStack, not a Git commit
- `detect-secrets` pre-commit hook (added Wave 1) prevents future regression
- Aligns dev workflow with production ExternalSecrets Operator pattern (would target a real
  SecretsManager backend in prod)

### Negative

- Rollout requires transient `flux suspend`/`resume` per service (Wave 2B)
- weave-gitops `cluster-user-auth` requires coordinated commit (ES + chart change together);
  cannot be split without a period where the Secret is unmanaged or double-owned
- LocalStack persistence must be preserved for secrets to survive pod restarts (already
  handled by `enableStartupScripts` idempotency check)
- One-time secret rotation on rollout: existing n8n-encrypted DB credentials become
  unreadable if the encryption key changes. **First-time rollout on a fresh dev cluster only**
  — existing dev n8n installations would need credential re-entry. Not applicable to prod
  (no n8n in prod yet).
