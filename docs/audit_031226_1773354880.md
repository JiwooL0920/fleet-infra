### ⚠️ Warning — Committed and Hardcoded Secrets

**Category:** Security
**Location:**
- `apps/base/localstack-init/secrets.env` — `PGADMIN_PASSWORD=secure-admin-password` (tracked in Git)
- `apps/base/n8n/helmrelease.yaml` — `encryption_key: "n8n-encryption-key-change-me"`
- `apps/base/weave-gitops/helmrelease.yaml` — hardcoded `passwordHash` (bcrypt)
- `apps/base/external-secrets-operator/secret.yaml` — `AWS_ACCESS_KEY_ID: "test"`, `AWS_SECRET_ACCESS_KEY: "test"`

**Source:** [Flux CD Secrets Management Guide](https://fluxcd.io/flux/security/secrets-management/)

**Current Pattern:**
Credentials are committed directly into YAML files and `.env` files tracked by Git. While the `.env` file at the repo root is gitignored, `apps/base/localstack-init/secrets.env` is not — it's a tracked file containing the pgAdmin password. The n8n encryption key is a placeholder string that would compromise encrypted data if used in any real workload. The ESO credentials are `"test"`/`"test"` but still hardcoded in a committed Secret manifest.

**Recommended Pattern:**
Per Flux CD security best practices, secrets should be managed through External Secrets Operator (already deployed), SOPS-encrypted secrets, or sealed secrets — never plaintext in Git. Even for local dev, the ExternalSecrets pattern is already established in this repo for 7 services. Extend it to cover all remaining credentials.

**Why This Matters:**
If this repository is ever made public (or shared with collaborators), all committed credentials are immediately exposed. The `detect-secrets` pre-commit hook exists but the baseline has already allowed these through. Even in local dev, building the habit of never committing secrets prevents costly mistakes when transitioning to production.

**Suggested Fix:**
1. Move `localstack-init/secrets.env` values into LocalStack Secrets Manager (same pattern as existing secrets)
2. Create ExternalSecrets for n8n encryption key and weave-gitops password
3. Replace the hardcoded ESO `secret.yaml` with a Kustomize secret generator or document clearly that `"test"` is the intentional LocalStack credential
4. Update `.secrets.baseline` after changes
5. Add `secrets.env` to `.gitignore` (or remove the file entirely)

### ⚠️ Warning — No CI/CD Pipeline

**Category:** DevOps & CI/CD
**Location:** Repository root — no `.github/workflows/`, `Jenkinsfile`, or equivalent

**Source:** [Flux CD Repository Structure Guide](https://fluxcd.io/flux/guides/repository-structure/) — recommends CI validation for GitOps repos. Also: [flux2-kustomize-helm-example](https://github.com/fluxcd/flux2-kustomize-helm-example) (1,239 stars) includes GitHub Actions for validation.

**Current Pattern:**
All validation runs exclusively via pre-commit hooks on the developer's machine. There is no server-side enforcement. A `git commit --no-verify` or a contributor without pre-commit installed would bypass all checks.

**Recommended Pattern:**
Flux's official example repository includes a GitHub Actions workflow that runs `flux build kustomization`, `kubeconform` validation, and `kustomize build` on every PR. This provides a safety net that cannot be bypassed locally.

**Why This Matters:**
Pre-commit hooks are a first line of defense, not the last. For a solo dev, the risk is manageable — you're unlikely to skip your own hooks. But the moment this repo is shared or you commit from a different machine (without hooks installed), broken manifests can land in the main branch and get deployed by Flux.

**Suggested Fix:**
Create `.github/workflows/validate.yaml` mirroring the [flux2-kustomize-helm-example CI workflow](https://github.com/fluxcd/flux2-kustomize-helm-example/blob/main/.github/workflows/e2e.yaml). At minimum, run:
1. `kustomize build` on all kustomization paths
2. `kubeconform` on rendered manifests
3. `yamllint` on all YAML files

**Estimated Effort:** S (< 1 day) — the pre-commit scripts already contain the validation logic; wrapping them in a GitHub Action is straightforward.

### ⚠️ Warning — CloudNativePG Missing Backup Configuration

**Category:** Resiliency / Correctness
**Location:**
- `apps/base/cloudnative-pg/cluster/cluster.yaml` — no `backup` spec in the Cluster CR
- No `ScheduledBackup` resource exists anywhere in the repo

**Source:** [CloudNativePG Backup Documentation](https://cloudnative-pg.io/docs/1.28/backup/) — "WAL archiving is essential for recovery objectives (RPO ≤ 5 minutes)"

**Current Pattern:**
The PostgreSQL Cluster CR defines instances, resource limits, monitoring, and managed databases — but has no `backup` section. No `ScheduledBackup` custom resource exists. The README and CLAUDE.md both state: "Automated backups to LocalStack S3" and "Daily backup schedule at 2:00 AM UTC" — but this is not reflected in any deployed manifest.

**Recommended Pattern:**
CloudNativePG supports native backup to S3-compatible storage (including LocalStack). The Cluster CR should include a `backup` section with `barmanObjectStore` pointing to LocalStack S3, and a `ScheduledBackup` resource for periodic base backups.

**Why This Matters:**
Documentation that doesn't match reality is worse than no documentation — it creates false confidence. If you're storing any meaningful data in PostgreSQL (n8n workflows, temporal state), a pod restart without proper WAL archiving means potential data loss. For a dev environment with expendable data the impact is low, but the documentation discrepancy is a real correctness issue.

**Suggested Fix:**
Either:
1. **Add backup config** — Add a `backup.barmanObjectStore` section to the Cluster CR pointing to LocalStack S3, and create a `ScheduledBackup` resource. CloudNativePG docs have a complete example.
2. **Or fix the documentation** — Remove backup claims from README/CLAUDE.md until backups are actually configured.

**Estimated Effort:** M (1-3 days) if implementing backups; S (< 1 hour) if just fixing docs

### ⚠️ Warning — Missing Flux Kustomization healthChecks

**Category:** Resiliency
**Location:** 7 Kustomizations in `base/services/` lack `healthChecks`:
- `grafana-config.yaml`, `grafana-operator.yaml`, `grafana-dashboards.yaml`
- `traefik-config.yaml` ← **critical dependency** (jaeger and scylla-cluster depend on it)
- `temporal.yaml`, `n8n.yaml`
- `crossplane-config.yaml` (disabled, lower priority)

**Source:** [Flux Kustomization API — Health Checks](https://fluxcd.io/flux/components/kustomize/kustomizations/#health-checks) — "Health checks are used to determine the rollout status of the deployed resources"

**Current Pattern:**
All 30 Kustomizations correctly use `prune: true` and `wait: true`, which is good. However, `wait: true` without `healthChecks` means Flux waits for resources to be applied but doesn't verify they're actually *healthy*. For `traefik-config`, this means downstream services (jaeger, scylla-cluster) may start deploying before Traefik IngressRoutes and middleware are fully functional.

**Recommended Pattern:**
Add `healthChecks` targeting the key resources in each Kustomization (Deployments, StatefulSets, HelmReleases). This ensures `dependsOn` references are truly meaningful — a downstream service won't start until the dependency is healthy, not just applied.

**Why This Matters:**
Without health checks, the fine-grained dependency graph (which is excellent architecture) loses much of its value. A Kustomization reports "ready" when resources are submitted to the API server, not when pods are running. This can cause cascading failures during initial deployment or after a Colima restart.

**Suggested Fix:**
Add healthChecks to at minimum the 4 non-Grafana Kustomizations. Example for `traefik-config.yaml`:
```yaml
healthChecks:
  - apiVersion: traefik.io/v1alpha1
    kind: IngressRoute
    name: traefik-dashboard
    namespace: traefik
```
For `n8n.yaml` and `temporal.yaml`, check the HelmRelease or Deployment readiness.

**Estimated Effort:** S (< 1 day) — Adding healthChecks is a YAML-only change, no code involved.

### ⚠️ Warning — Pre-commit Validation Blind Spots

**Category:** Testing / DevOps
**Location:**
- `scripts/pre-commit/validate-manifests.sh` — only scans `./clusters` with `maxdepth 2`
- `scripts/pre-commit/validate-kustomize.sh` — skips kustomizations with Flux-specific fields (postBuild, dependsOn, healthChecks)
- `.pre-commit-config.yaml` — `kustomize-build` hook excludes `clusters/` and `base/services/`

**Source:** [kubeconform documentation](https://github.com/yannh/kubeconform) — validates Kubernetes manifests against schemas. [Flux validation guide](https://fluxcd.io/flux/guides/repository-structure/) recommends validating all manifests in CI.

**Current Pattern:**
The `validate-manifests.sh` script runs `kubeconform` only on files under `./clusters` with `maxdepth 2`. This means **all 19+ service manifests under `apps/base/`** are never validated by kubeconform. Additionally, `validate-kustomize.sh` skips any kustomization containing Flux-specific fields — which is most of the service kustomizations in `base/services/`. The kustomize-build pre-commit hook explicitly excludes `clusters/` and `base/services/`.

**Recommended Pattern:**
Run kubeconform on `apps/base/` manifests as well (using `--ignore-missing-schemas` for CRDs). For Flux kustomizations, use `flux build kustomization` instead of `kustomize build` to handle Flux-specific fields. The official flux2-kustomize-helm-example repo demonstrates this pattern.

**Why This Matters:**
The majority of actual Kubernetes manifests (HelmReleases, namespaces, ExternalSecrets, CNPG clusters) live under `apps/base/` and are never validated pre-commit. A typo in a HelmRelease spec, a malformed ExternalSecret, or an invalid CNPG cluster definition would only be caught after Flux attempts to apply it.

**Suggested Fix:**
1. Extend `validate-manifests.sh` to also scan `apps/base/` with appropriate `--ignore-missing-schemas` for CRDs
2. Replace `kustomize build` with `flux build kustomization` in validation scripts for Flux-specific kustomizations
3. Remove the `clusters/` and `base/services/` exclusions from the kustomize-build pre-commit hook, or add a separate hook using `flux build`

**Estimated Effort:** S (< 1 day) — Script modifications, no infrastructure changes.

### ℹ️ Info — Non-Pinned Container Image Tags

**Category:** Correctness / DevOps
**Location:**
- `apps/base/redis-sentinel/helmrelease.yaml` — uses `tag: latest` for Redis image
- `base/services/environment.env` — most chart versions are properly pinned via variables (positive), but the Redis container image tag is not

**Source:** [Flux CD HelmRelease Best Practices](https://fluxcd.io/flux/components/helm/helmreleases/) — recommends pinning chart versions; by extension, container image tags should also be pinned for reproducibility.

**Current Pattern:**
The Redis Sentinel HelmRelease uses `image.tag: latest` in its values. All other HelmReleases use chart version variables from `environment.env`, which is good centralized version management.

**Recommended Pattern:**
Pin the Redis image tag to a specific version (e.g., `7.2.4-debian-12-r9`) in `environment.env` alongside other version variables.

**Why This Matters:**
`latest` means every pod restart could pull a different image version, potentially introducing breaking changes silently. In a dev environment this is lower risk, but it makes debugging harder when behavior changes unexpectedly.

**Suggested Fix:**
Add `REDIS_IMAGE_TAG=7.x.x` to `environment.env` and reference it in the HelmRelease values.

**Estimated Effort:** S (< 1 hour)

### ℹ️ Info — Kubernetes Security Hardening Gaps

**Category:** Security
**Location:**
- All 16 `namespace.yaml` files under `apps/base/` — no pod-security labels
- Majority of HelmReleases — no `securityContext` (runAsNonRoot, readOnlyRootFilesystem, etc.)
- No `NetworkPolicy` resources anywhere in `apps/base/`

**Source:** [Kubernetes Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/) — recommends `pod-security.kubernetes.io/enforce: baseline` at minimum on all namespaces.

**Current Pattern:**
Namespaces are created without pod security admission labels. Most HelmRelease values don't configure security contexts (exceptions: metrics-server, promtail, weave-gitops, pgadmin4 do set some security context fields). No NetworkPolicies exist to restrict inter-pod traffic.

**Recommended Pattern:**
Apply at minimum `pod-security.kubernetes.io/enforce: baseline` labels to all namespaces. Add `securityContext` blocks to HelmRelease values where feasible.

**Why This Matters:**
For a local dev cluster with a single user, the blast radius is minimal. However, establishing these patterns now makes it trivial to carry them forward if any of these services graduate to a shared or production environment. It's also a good habit for muscle memory.

**Suggested Fix:**
Add to each `namespace.yaml`:
```yaml
metadata:
  labels:
    pod-security.kubernetes.io/enforce: baseline
    pod-security.kubernetes.io/warn: restricted
```

**Estimated Effort:** S (< 1 day) — YAML-only changes across namespace files. Can be templated.

### ℹ️ Info — Flux Configuration Consistency Gaps

**Category:** Resiliency / Correctness
**Location:**
- 8 Kustomizations missing `retryInterval`: `loki.yaml`, `external-secrets-config.yaml`, `crossplane-config.yaml`, `traefik-config.yaml`, `promtail.yaml`, `temporal.yaml`, `n8n.yaml`, `crossplane-providers.yaml`
- 2 HelmReleases missing remediation blocks: `traefik`, `redis-sentinel`
- Inconsistent `interval` formatting: mix of `5m`, `10m0s`, `1h`
- `grafana-operator.yaml` and `grafana-config.yaml` use `1h` interval — slow feedback for dev

**Source:** [Flux Kustomization API](https://fluxcd.io/flux/components/kustomize/kustomizations/) — recommends `retryInterval` for recovery from transient errors. [Flux HelmRelease API](https://fluxcd.io/flux/components/helm/helmreleases/) — recommends `install.remediation` and `upgrade.remediation`.

**Current Pattern:**
Most Kustomizations and HelmReleases follow Flux best practices, but there are inconsistencies. 8 out of 30 Kustomizations lack `retryInterval`, meaning transient failures require waiting for the full `interval` cycle before retrying. Two HelmReleases lack remediation blocks while the rest have `retries: 3`.

**Recommended Pattern:**
Standardize all Kustomizations with `retryInterval: 2m0s` (Flux default recommendation). Add `install.remediation.retries: 3` and `upgrade.remediation.retries: 3` to traefik and redis-sentinel HelmReleases. Normalize interval format to `10m0s` style.

**Why This Matters:**
These are not causing active problems, but inconsistency makes the codebase harder to maintain. When debugging a failed reconciliation, you'd expect consistent retry behavior across all services.

**Suggested Fix:**
Add `retryInterval: 2m0s` to the 8 Kustomizations. Add remediation blocks to traefik and redis-sentinel HelmReleases (copy from any existing HelmRelease). Consider reducing grafana-operator/grafana-config interval to `10m0s` for dev.

**Estimated Effort:** S (< 1 hour) — Batch YAML edits.

### ℹ️ Info — Tooling and Script Quality Issues

**Category:** Correctness / DevOps
**Location:**
- `Makefile` line referencing `scripts/verify-startup.sh` — file does not exist
- `scripts/port-forward.sh` — missing `set -euo pipefail`, no `trap` for background PID cleanup
- `scripts/fix-control-plane-ip.sh` — missing `-u` and `pipefail` flags
- `.pre-commit-config.yaml` — ShellCheck excludes 3 operational scripts

**Source:** [ShellCheck](https://www.shellcheck.net/) — standard shell script linter. [Google Shell Style Guide](https://google.github.io/styleguide/shellguide.html) — recommends `set -euo pipefail` in all scripts.

**Current Pattern:**
Script quality varies. `get-ui-credentials.sh` and `setup-local-dns.sh` properly use `set -euo pipefail`, but `port-forward.sh` and `fix-control-plane-ip.sh` don't. The Makefile references a `verify-startup.sh` script that doesn't exist (broken target). Three scripts are excluded from ShellCheck linting.

**Recommended Pattern:**
All scripts should use `set -euo pipefail`. Background processes should be cleaned up via `trap`. Makefile targets should only reference scripts that exist.

**Why This Matters:**
A script without `set -e` will continue executing after errors, potentially leaving the system in an inconsistent state. The missing `verify-startup.sh` reference means a Makefile target silently fails. For a personal project these are minor annoyances, not critical issues.

**Suggested Fix:**
1. Add `set -euo pipefail` to `port-forward.sh` and `fix-control-plane-ip.sh`
2. Add `trap 'kill $(jobs -p) 2>/dev/null' EXIT` to `port-forward.sh` for background PID cleanup
3. Remove or create the missing `verify-startup.sh` reference in Makefile
4. Remove ShellCheck exclusions and fix the flagged issues

**Estimated Effort:** S (< 1 day)

## Part 2: Narrative Summary

### Executive Overview

Fleet-infra is a well-architected GitOps repository that demonstrates strong Flux CD patterns — particularly the fine-grained dependency graph, centralized configuration management, and consistent use of External Secrets Operator. For a personal/local dev project, it's significantly more mature than typical. The main areas for improvement are **secrets hygiene** (hardcoded credentials committed to Git), **validation coverage** (pre-commit hooks have blind spots), and **documentation accuracy** (backup claims that don't match deployed manifests).

### What's Done Well

1. **Fine-grained dependency graph** — 30 service-level Kustomizations with precise `dependsOn` relationships enabling parallel deployment. No circular dependencies. This is best-in-class Flux usage.
2. **Centralized variable substitution** — Chart versions, resource limits, and environment-specific settings all managed through `environment.env` and `cluster-vars-patch.yaml`.
3. **ExternalSecrets pattern** — Consistently applied across 7 services with idempotent LocalStack initialization.
4. **Resource limits everywhere** — All HelmReleases have explicit requests and limits, preventing resource starvation.
5. **Pre-commit validation** — Multi-layered local validation (yamllint + kubeconform + kustomize build + ShellCheck + detect-secrets + Flux version checks).
6. **All Kustomizations use `prune: true` and `wait: true`** — Proper garbage collection and ordered deployment.
7. **Declarative database management** — CloudNativePG databases configured declaratively for all applications.
